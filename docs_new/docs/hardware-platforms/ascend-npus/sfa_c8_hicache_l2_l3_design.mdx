# SFA C8 HiCache L2/L3 设计

状态：设计审查修订版 v2；本次变更不包含运行时代码。

基线：`glm52-910b-w4a8c8-sfa-c8-pd-20260905`
（`bcd4b0a39ced7293c7005c63684f8677170ed2a8`）。

正文使用中文；为与源码、命令行参数和协议字段一一对应，`target`、`draft`、
`sidecar`、`fail closed` 等代码术语保留英文。

## 审查后的关键修正

第一版的产品边界基本正确，但部分实现假设与当前 HiCache 代码契约不一致。
本版作出以下修正：

1. 紧凑 SFA 主缓存作为物理 `PoolName.KV` 锚点，负责逻辑主机页分配和
   Mooncake 基础对象；BF16 Lightning Indexer 作为复用锚点索引的
   `ALL_PAGES` 旁路池。SFA C8 不使用 `LogicalHostPool`，也不需要第三个
   marker 对象。
2. 在通用 MLA 回退策略之前新增 SFA 专用缓存栈策略。当前代码若直接打开
   HiCache，会错误构造要求 BF16 独立 K/V 的 `MLATokenToKVPoolHost`。
3. 组件描述符使用“每个物理层、每个完整页行的字节数”，不再使用含义模糊的
   “每 token/每 page item bytes”。
4. `--hicache-size` 或 `--hicache-ratio` 定义一个由主缓存、Indexer 及必要
   draft 状态共同使用的逻辑页总预算，不能分别对各池重复应用。
5. Mooncake `group_ids` 是放置/副本机制，不是跨两次 `batch_set` 的事务。
   正确可见性由“旁路对象先写、基础对象最后写、查询时校验全部对象”保证。
6. 当前控制器仅根据 `MLATokenToKVPool` 类型就认定缓存跨 TP rank 完全复制，
   非 0 rank 会跳过 L3 写入。SFA C8 必须先实测证明字节一致，不能静默继承
   这个判断。
7. 昇腾后端目前会把所有 MLA HiCache 强制改成 `page_first_kv_split`。SFA C8
   必须选择 opaque page-first 布局和专用 `kernel_ascend` 拷贝路径，不能复用
   BF16 K/V split 算子。
8. 当前生产清单在 P、D 两侧都启用了 NEXTN。静态调用链已经证明，NEXTN
   会解析为 EAGLE，并在 P 侧创建独立的 draft `TpModelWorker` 和 KV pool；
   因此 draft 紧凑主缓存与 draft Indexer 都是必需旁路状态，不能假设 draft
   只存在于 D，也不能把它当作 target 的别名。

## 背景与目标

当前昇腾 GLM-5.2 部署将主 SFA 缓存保持为原生 C8 紧凑表示，并以相同表示在
Prefill 与 Decode worker 之间传输。这样接近翻倍了设备缓存容量，但 P worker
仍只有本地 L1 radix cache。缓存被淘汰或同一会话被调度到另一个 P DP 后，前缀
仍需重新计算；连续冷长输入会降低命中率并放大队头阻塞。

现有昇腾 HiCache 不能直接用于该布局。它的 MLA host pool 和
`kernel_ascend` 路径要求独立的 BF16 `k_buffer`、`v_buffer` 与 Indexer；
而 SFA C8 实际持有：

- 78 个紧凑主缓存层，每 token 每层 656 个 opaque bytes；
- 21 个物理 Lightning Indexer 层，每 token 每层 128 个 BF16 值。

若把紧凑字节当作普通 K/V，可能把 C8 展开回 BF16、传输错误布局，或让缺少
Indexer 的前缀被错误发布。所有缓存层级都必须逐字节保留当前设备表示。

本设计目标如下：

1. 为 P 侧增加不展开 BF16 的 SFA C8 主机 L2。
2. 增加 Mooncake L3，使兼容的 P 副本可以复用被淘汰的前缀。
3. 主缓存、Indexer 及必要 draft 状态共用一个逻辑页索引和一次有效性判断。
4. 保持现有紧凑 P-to-D 传输及 D 侧 MTP3 行为不变。
5. 布局、拓扑、版本或组件不完整时一律 fail closed。
6. 提供足够的指标和故障注入，线上可区分 L1、L2、L3 与重新计算路径。

## 不在本阶段范围内

- 不启用 D 侧 HiCache，不改变 D retract/rebootstrap 行为。
- 不修改 SFA 量化、QSFA 算子、CUDA/NPU Graph 或当前 P-to-D Mooncake 传输
  协议。
- 不在本阶段新增 rank-sharded L3；若不能证明 rank replicated，L3 保持关闭。
- 不要求 NPU 直接写 L3，首期链路为 NPU L1 → 主机 L2 → Mooncake L3。
- 不修改 admission 和调度策略。

## 当前代码边界

`NPUMLATokenToKVPool` 已为 P-to-D 正确暴露紧凑描述：

- 每个紧凑主缓存层一条连续页行；
- 每个物理 Indexer 层一条连续页行；
- 不伪造 K/V split。

但 SFA C8 的 `supports_cpu_offload` 当前明确为 false，
`get_cpu_copy`/`load_cpu_copy` 也会拒绝该布局。HiCache assembler 尚无 SFA
策略。由于 `NPUMLATokenToKVPool` 继承 `MLATokenToKVPool`，通用路径会错误
选择 BF16 MLA host pool。在完整的 grouped L2 通过验证前，这些保护不得移除。

GLM-5.2 作为 DSA 模型进入 unified radix/HiCache 路径，因此新策略应放在
`hybrid_pool_assembler.py`。旧 `HiRadixCache` 路径也必须显式 fail-fast，
防止未来 registry 调整后再次落入通用 MLA 分支。

## 数据布局与容量

target 和 P 侧 NEXTN draft 缓存都保持与设备完全相同：

| 组件 | 物理层数 | 每 token 每层字节 | 每 token 每 rank 字节 | 每 128-token 页每 rank 字节 |
| --- | ---: | ---: | ---: | ---: |
| SFA 紧凑主缓存 | 78 | 656 | 51,168 | 6,549,504 |
| Lightning Indexer 旁路缓存 | 21 | 256 | 5,376 | 688,128 |
| NEXTN draft 紧凑主缓存 | 1 | 656 | 656 | 83,968 |
| NEXTN draft Indexer | 1 | 256 | 256 | 32,768 |
| target 小计 |  |  | 56,544 | 7,237,632 |
| 生产必需组件合计 |  |  | 57,456 | 7,354,368 |

Indexer 单层单 token 大小为 `128 * sizeof(BF16) = 256` 字节。因此一个
128-token 逻辑页的 target payload 每 rank 为 7,237,632 字节，即
6.90234375 MiB；加上独立 NEXTN draft 后，生产必需 payload 为 7,354,368
字节，即 7.013671875 MiB。

当前设备池为 138,112 tokens。ratio=2 时，每 rank 为 2,158 个主机页、
276,224 个主机 token slots。target 两组件的精确 payload 为
15,618,809,856 字节，即 15.619 GB 或 14.546 GiB；NEXTN draft 再增加
251,916,288 字节，即 0.252 GB 或 0.235 GiB。生产必需组件合计为
15,870,726,144 字节，即 15.871 GB 或 14.781 GiB，尚未包含 allocator
元数据和对齐开销。

启动日志必须同时报告 per-rank 和 P 节点所有 rank 的合计主机内存需求。只看
per-rank 数值不足以判断节点是否安全。

### 单一逻辑页预算

所有必需物理池使用相同的 `num_host_pages`：

```text
required_page_bytes = target_main + target_indexer + required_draft_components

if hicache_size > 0:
    num_host_pages = floor(hicache_size_bytes / required_page_bytes)
else:
    num_host_pages = floor(device_pages * hicache_ratio)

host_token_slots = num_host_pages * 128
```

`hicache_size_bytes` 沿用 CLI 的十进制 GB 口径。builder 先对所有必需组件的
总和及现有 host memory reserve 做一次预检，再以相同逻辑页数分配各物理池。
把用户指定的 GB 分别用于 main、Indexer 或 draft，会造成重复分配，属于发布
阻断问题。

## 正确的主机缓存池架构

一个逻辑页 ID 对应四个生产必需物理页池：

```text
logical page id N，由 packed-main anchor 分配
  PoolName.KV[N]:            [78, 128, 1, 656] int8
  PoolName.INDEXER[N]:       [21, 128, 1, 128] bfloat16
  PoolName.DRAFT[N]:         [ 1, 128, 1, 656] int8
  PoolName.DRAFT_INDEXER[N]: [ 1, 128, 1, 128] bfloat16
```

缓存栈为：

```text
HostPoolGroup
  anchor:  PoolName.KV            -> target packed main 物理 host pool
  sidecar: PoolName.INDEXER       -> target BF16 indexer 物理 host pool
  sidecar: PoolName.DRAFT         -> draft packed main 物理 host pool
  sidecar: PoolName.DRAFT_INDEXER -> draft BF16 indexer 物理 host pool

  所有 sidecar:
    indices_from_pool=PoolName.KV
    hit_policy=ALL_PAGES
```

packed-main host pool 负责 allocation、free、eviction 和基础 storage key，
而不是使用零字节的 `LogicalHostPool`。这与当前 `HybridCacheController`
一致。生产配置每个逻辑页恰好产生四个物理对象，但只能有一个 allocator，
也不需要额外 commit marker。

### SFA 专用策略

在 `_PlainKvStrategy` 之前增加 `_SfaC8Strategy`，只匹配：

- device pool 为 `NPUMLATokenToKVPool`；
- `sfa_c8_enabled` 为 true；
- unified cache components 为 `{ComponentType.FULL}`；
- 第一阶段进程角色为 Prefill。

该策略先构建 target 的两个 entry；NEXTN draft 注册阶段再把 draft 的两个
entry 加入同一个 `HostPoolGroup`。两个 Indexer 的 layer mapper 都必须来自各自
device pool 的 `indexer_layer_id_to_slot`：控制器迭代的是模型 layer ID，host
Indexer 只保存物理 owner layer。若简单按 buffer 下标映射，会把 Indexer 数据
恢复到错误模型层。

旧 `HiRadixCache` 在接入同一个 builder 之前必须显式拒绝 SFA C8，不能回退到
`MLATokenToKVPoolHost`。

### 必须修改的代码边界

实现不能只新增一个 host pool 类，还必须同时收敛以下边界：

1. `PoolName` 新增 `DRAFT_INDEXER`，并把它纳入 Mooncake 的单对象 page-packed
   sidecar key 生成和 buffer 注册逻辑。
2. `hybrid_pool_assembler.py` 新增 `_SfaC8Strategy`，创建 target anchor 与
   target Indexer sidecar；不得命中通用 MLA fallback。
3. `maybe_register_hicache_draft` 不再单独创建
   `mem_pool_host_draft`，而是把 draft main 和 draft Indexer 加入同一个
   `HostPoolGroup`。四组件 group 完成前，不得启动缓存后台 I/O。
4. `HybridCacheController` 的一次 backup/load operation 同时携带四个
   `PoolTransfer`；移除这条路径上的 `_draft_page_set/_get` best-effort 补写。
5. `MooncakeStore.register_mem_host_pool_v2` 不能再假设 `PoolName.DRAFT` 只有一个
   普通 MLA/MHA `kv_buffer`，必须按 SFA 组件描述符注册 opaque page region。
6. L3 查询、写入、取消和回滚统一使用 group completion 状态；禁止 target
   controller 与 draft controller 各自发布命中。

这些改动必须在同一个实现 PR 中完成。若只完成其中一部分，启动门禁必须继续
拒绝 SFA C8 + HiCache + NEXTN。

## 布局无关的设备契约

device pool 是布局的唯一事实来源。组件描述符描述完整页行，不在其他模块重建
shape：

```python
@dataclass(frozen=True)
class OpaquePageComponent:
    name: PoolName
    device_buffers: tuple[torch.Tensor, ...]
    page_row_nbytes: int
    layer_id_to_buffer_slot: Mapping[int, int]
    required_for_hit: bool = True
```

当前模型中，packed-main 的 `page_row_nbytes` 为 83,968（`128 * 656`），
Indexer 为 32,768（`128 * 128 * 2`）。启动时根据真实 tensor 验证同一组件内
所有 buffer 的 row size、dtype、page count 和 contiguity 一致。

该描述符应尽量与现有紧凑 P-to-D metadata 共用，但 HiCache 不能只依赖指针
列表顺序；组件名和 layer mapping 必须进入显式契约。

## L1 与 L2 之间的传输

### 正确性参考路径

每个 page-aligned operation 执行：

1. 不转换地拷贝 78 个 packed-main 页行；
2. 不转换地拷贝 21 个物理 Indexer 页行；
3. 不转换地拷贝 1 个 draft packed-main 页行；
4. 不转换地拷贝 1 个 draft Indexer 页行；
5. 全部必需状态完成后记录一个 completion event；
6. event 成功后才向 radix tree 发布 host node。

首个实现可以用显式 indexed tensor copy，先证明逐字节 round trip 和 logits
正确，再优化性能。

当前 NPU 默认会把所有 MLA HiCache 改为 `page_first_kv_split`，并走
`transfer_kv_dim_exchange`。这对 packed SFA 无效。SFA C8 开启时，builder
必须选择 opaque page-first 内部布局，同时保留 `kernel_ascend` 后端；随后增加
专用 opaque-row D2H/H2D kernel。整个过程禁止反量化、K/V split、head
transpose 或 layer duplication。

### 分配、完成与取消

anchor 分配统一的 host indices，sidecar 只派生相同 indices，不拥有独立 free
list。D2H 必须在所有必需组件完成后才 ack。失败或取消时不发布 radix node，
anchor allocation 只释放一次，不能再次释放 sidecar。

H2D 在拷贝任何组件前先预留 device slots。只有所有参与 attention rank 都恢复
全部必需组件，请求才算 cache hit。任一组件或 rank 失败，都释放新 device slots
并回退到正常 Prefill 重算。

第一阶段仍保持 `supports_cpu_offload=false`。HiCache prefix reload 与 D 侧
retract 的生命周期不同，实现前者不能隐式打开后者。

## L2 与 L3 Mooncake 之间的存储

### 对象与 key

沿用当前 v2 base/sidecar 命名，不在调用方手工拼 SFA 专用 key：

```text
packed-main 基础对象：<page-hash><mla-suffix>_k
indexer 旁路对象：    <page-hash><mla-suffix>_indexer
draft 主缓存对象：    <page-hash><mla-suffix>_draft_k
draft indexer 对象：  <page-hash><mla-suffix>_draft_indexer
```

精确分隔符由 `MooncakeStore` 管理；调用方只传 logical page hash 和 `PoolName`。
四个 key 之前统一添加确定性的 cache identity tag。调用方不能自行拼接
`<tp-rank>` 或组件后缀。

page size=128 时，base 对象为 6,549,504 字节，target Indexer 对象为 688,128
字节，draft 主缓存对象为 83,968 字节，draft Indexer 对象为 32,768 字节。
四个 page-first host region 都必须注册到 Mooncake，供 v2 路径执行 zero-copy
host I/O。上述文本只表达语义，最终 key 的精确拼写必须由 `MooncakeStore`
根据 `PoolName` 统一生成。

### 故障时关闭可见性，不假设事务

写入顺序为：

1. 依次写 target Indexer、draft 主缓存和 draft Indexer；
2. 最后写 packed-main base object；
3. 所有必需写入均成功后才报告 page complete。

查询先检查 base prefix，再对每个必需 sidecar 使用 `ALL_PAGES`，最终取所有
组件连续命中前缀的最小值。若在 base 写入前崩溃，只会留下不可见的 orphan
sidecar；base 存在但任一 sidecar 缺失时仍为 miss。orphan 由正常 TTL/eviction
异步清理。

可启用 Mooncake `group_ids` 以改善组件共址或副本放置，但不能宣称它在独立的
base 与 sidecar `batch_set` 之间提供原子提交。关闭 group semantics 或所装
Mooncake 不支持 `group_ids` 时，正确性也必须成立。

读取时先把 base 放入 host memory，再读取 sidecar；所有 read 完成前，host
page 不得对 H2D 可见。

### 缓存身份与请求 key

L3 namespace 使用确定性 digest，至少覆盖：

- model weights 和 tokenizer revision；
- packed layout version、tile size、quant mode、scale representation；
- page size 及 main/indexer 物理 layer ownership；
- attention TP/CP/PP topology 与 storage replication mode；
- framework compatibility version；
- target/draft cache role。

digest 通过 storage backend tag/namespace 传入，并在启动时记录。现有 radix
`extra_key` 语义必须保留，包括 LoRA identity、cache salt 和 multimodal hash。
L3 不得把 salted 或 adapter-specific key 退化为仅 token IDs。若安全策略要求
租户级缓存隔离，在共享 L3 前把 tenant identity 加入 `extra_key` 或 namespace。

identity 不匹配是正常 cache miss，绝不能 best-effort restore。

## TP 分片存储前置门槛

L2 始终是 per process/per rank，因为每张 NPU 都需要本地设备状态；L3 去重是
另一个独立问题。

当前 `HiCacheController` 对所有 `MLATokenToKVPool` 设置
`is_rank_replicated=true`，使非 0 TP rank 跳过 backup，并从 MLA 对象后缀中
省略 TP rank。SFA C8 目前只是因为继承关系获得该行为，不是经过验证的契约。

启用 L3 前，要对完整 attention TP group 的所有必需组件做 byte checksum 和
restored-logit 对比，覆盖 cold、chunked、L1-hit 和 L2-hit prefix。判定规则为：

- 若所有必需组件跨 rank 逐字节一致，声明
  `storage_replication_mode=replicated`，L3 保留一套对象，由 rank 0 写入，
  每个 rank 将相同字节恢复到自己的 L1；
- 若任一组件不同，L3 保持关闭，直到 storage config 支持显式 rank-sharded
  mode，且每个 rank 都有独立 key 和读写责任。

最终实现不能继续通过 `isinstance(..., MLATokenToKVPool)` 推断该属性，应由
device pool 显式声明 capability。CP rank 若持有不相交 cache slice，仍须使用
独立 identity/key。

## MTP 与 PD 范围

第一阶段只在 P worker 开启 L2/L3：

```text
request -> PD Router -> Prefill L1
                         | miss
                         v
                       host L2
                         | miss
                         v
                     Mooncake L3
                         | miss
                         v
                      recompute
                         |
                         v
              现有 packed C8 P-to-D transfer -> Decode MTP3
```

当前生产清单在 P、D 两侧都启用了 NEXTN/MTP3。基线代码中的调用链为：

```text
NEXTN -> EAGLE -> EAGLEWorkerV2 -> EagleDraftWorker
      -> 独立 TpModelWorker -> 独立 draft KV pool
```

`DefaultPoolConfigurator` 在 SFA C8 + DSA + EAGLE 路径中，也明确按 1 个 NEXTN
物理层为每 token 增加 656 字节紧凑主缓存和 256 字节 Indexer。这证明当前 P
侧 draft 不是 target 别名，必须与 target 前缀一起保存和恢复。

现有 `maybe_register_hicache_draft` 虽然会注册独立 draft host pool，但由于 draft
pool 同样继承 `MLATokenToKVPool`，它会错误构造 BF16
`MLATokenToKVPoolHost`。现有 Mooncake draft 路径又只支持一个对象并采用
best-effort 语义，无法表达“draft 紧凑主缓存 + draft Indexer”的完整提交。

修正后的实现要求：

1. 使用 `PoolName.DRAFT` 表示 draft 紧凑主缓存，使用新的
   `PoolName.DRAFT_INDEXER` 表示 draft Indexer；两者都是 target base 的
   `ALL_PAGES` 旁路池。
2. 四个物理组件共用相同 logical page count、cache identity 和 host page
   indices；draft 的 116,736 字节/页计入单一 host budget。
3. L3 依次写 target Indexer、draft 主缓存、draft Indexer，最后写 target base；
   任一对象缺失都必须缩短可用前缀，不能沿用 best-effort draft 命中。
4. 运行时门禁仍须核对 P 侧 draft 的真实 shape、dtype、layer map 和 row bytes；
   若与上述静态契约不同则拒绝启动，不能退回通用 MLA host pool。

D 的 MTP 生命周期和现有 P-to-D wire protocol 不在本项目中改变。

PD Router 首选保持 P-DP cache affinity。L3 只在 cache identity 兼容的 P
副本间共享，因此另一 P DP 可恢复已淘汰前缀，而不改变 D placement。

D 侧 L2 是后续独立阶段。不能仅翻转 `supports_cpu_offload` 就启用，因为 D
retraction、generated-token ownership 和 rebootstrap 与 P prefix reuse 不同。

## 故障语义

逻辑页状态机为：

```text
allocated -> copying -> complete -> published -> evictable
                |           |
                +-> failed <-+
```

- 只有 main、Indexer 和必要 draft 全部 complete 才能对 radix tree 可见。
- complete 覆盖所有参与的 attention rank。
- D2H、H2D 或 L3 I/O 取消会使 destination page 无效。
- L3 timeout 遵循既有策略，随后回退 recompute。
- Mooncake 故障降级为 L2/L1/recompute，不应使 P unhealthy。
- 显式配置的 host size 无法分配时启动失败，不静默缩容。
- 对象大小、layout identity 或组件数量错误时 fail closed 为 miss，并增加专用
  error counter。
- sidecar 成功但 base 未写入时是 orphan，不是 hit。

## 实现完成后的配置

最终路径沿用现有用户参数，初始配置如下：

```bash
SGLANG_NPU_ENABLE_SFA_C8=1

--enable-hierarchical-cache
--hicache-ratio 2.0
--hicache-write-policy write_through_selective
--hicache-load-back-threshold 8192
--hicache-io-backend kernel_ascend
--hicache-mem-layout page_first
--hicache-storage-backend mooncake
--hicache-storage-prefetch-policy timeout
```

容量来源只选一个：`--hicache-ratio` 或经过验证的 `--hicache-size`。SFA 策略
将用户指定的 page-first 解释为 opaque page-first，并阻止通用 NPU MLA 逻辑将其
改写为 `page_first_kv_split`。

storage extra config 必须包含确定性的 cache identity tag。group semantics 仅
作为优化开关，正确性不能依赖它。

各阶段实现前继续 fail-fast：

- grouped L2 未实现前，拒绝 SFA C8 + HiCache；
- identity 与 rank mode 未验证前，拒绝 SFA C8 + Mooncake；
- P 侧 draft pool 未实现四组件一致性或运行时契约不符时拒绝启动；
- P-only 阶段始终拒绝 D 侧 SFA C8 HiCache。

`write_through_selective` 和 8K load-back threshold 只是起测值，不是发布常量。
C8 改变了传输字节数，必须重新测量写入与恢复相对重算的盈亏点。

## 可观测性

指标按 cache tier 和 component 拆分：

- L1/L2/L3 lookup、hit tokens、miss tokens 和有效命中率；
- D2H、H2D、L3 read/write bytes 与 duration；
- logical page 的 pending、complete、evicted、cancelled、partial-failed 数量；
- packed-main、Indexer 与必要 draft 的传输失败数；
- timeout、corruption 或 identity mismatch 后的 fallback recompute tokens；
- orphan sidecar 数量与清理结果；
- per-rank 及 per-node 汇总的 host pool used/total bytes；
- Mooncake object error，以及 group semantics 是否实际启用。

采样请求日志记录所选 tier、logical page count、cache identity digest、storage
replication mode 和 fallback reason；不得记录 prompt、credential 或 raw cache
bytes。

## 验证计划

### 验证门禁 0：布局、draft 与分片特征确认

实现启用前：

1. 在每个 P rank 上断言真实 packed/indexer shape、dtype、physical layer map、
   row bytes 与 contiguity。
2. 从实际 tensor 计算并核对 83,968、32,768 和 7,237,632 字节，不依赖模型
   常量。
3. 核对实际 P-side draft pool 是独立的 1 层 packed main + 1 层 Indexer，并验证
   每页分别为 83,968 和 32,768 字节；不一致时拒绝启动。
4. 对 1K、8K、64K、126K 的 cold/chunked prefix，比对 attention TP group
   所有必需组件。
5. 决定并记录显式 L3 storage replication mode。

### 单元与纯 CPU 测试

1. strategy selection 必须先命中 SFA，不得进入 generic MLA。
2. 单一总字节预算必须为所有 required pool 生成相同 logical page count。
3. 组件描述符必须拒绝错误 dtype、row size、layer map 或 alignment。
4. main/indexer 使用不同 source/destination physical page mapping 时，host round
   trip 仍逐字节一致。
5. main allocation/free 由 sidecar 共用，不能 double-free。
6. 任一 target/draft sidecar 缺失、变短或 identity 错误时，必须缩短可用前缀。
7. storage 必须先写全部 sidecar、最后写 base；在每个边界注入失败都不能形成
   hit。
8. Mooncake v2 对生产配置的每页恰好产生一个 base 和三个 sidecar 对象，且在
   支持或不支持 `group_ids` 时写入顺序均稳定。
9. 现有 BF16 MLA、MHA、DSA、DeepSeek V4、MTP 及非 HiCache 路径不变。

### 昇腾集成矩阵

每个阶段均使用隔离 candidate deployment，不覆盖已打 tag 的基线：

| 阶段 | L2 | L3 | PD | 必须取得的证据 |
| --- | --- | --- | --- | --- |
| A | 开 | 关 | 关 | byte checksum、logits、L1 淘汰后从 L2 恢复 |
| B | 开 | 关 | 仅 P 开 | L2 恢复后 packed P-to-D 传输正确 |
| C | 开 | Mooncake TCP | 仅 P 开 | 跨 P-DP L3 命中与 timeout fallback |
| D | 开 | Mooncake RDMA | 仅 P 开 | 带宽、长尾、重启恢复 |

每个阶段覆盖 127/128/129、255/256/257 页边界；1K、8K、16K、64K、126K 及
至少一个 200K prefix；chunked prefill；physical page remapping；并发淘汰；
D-side MTP3；graph decode；streaming；tool calls；client cancellation；P/D
restart。

使用固定 sampling 和 prompt logprobs 或 last-prefill logits 对比 cold、L1、L2、
L3 路径。不得出现超出既有 C8 容差的分叉、乱码、重复循环、缺少最终答案或
usage 计数错误。

### 性能验收

- 开启 L2 后，cold/L1-miss input throughput 回退不超过 3%。
- L2 hit 在所选 threshold 上必须快于 recompute，并显著改善 16K+ prefix TTFT；
  否则提高 threshold。
- L3 hit 在经验证的 prefix 长度上必须快于 recompute，包括 P90 storage latency。
- 真实混合流量下 Decode P90 TPOT 和 output throughput 回退不超过 5%。
- retract/rebootstrap failure、HCCL/Mooncake session loss、host OOM、device OOM
  不得增加。
- 完成 2 小时真实画像回放和 48 小时 2 倍速回放，取得分层 cache metrics，且
  无缓存相关正确性问题。
